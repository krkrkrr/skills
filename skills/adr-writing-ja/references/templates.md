# ADR テンプレート集（日本語）

該当する骨組みを新しいファイルに写し、角括弧の部分を埋める。
出典は帰属のために記す。
各欄の詳しい説明が必要なら、上流リポジトリ（`locales/ja/テンプレート/` に日本語訳がある）を参照する。

ステータス値は、どのテンプレートでも英語のキーワード（`Proposed`、`Accepted`、`Rejected`、`Deprecated`、`Superseded by ADR-NNNN`）で書く。
テンプレート固有の状態名（Tyree と Akerman の pending など）がある場合も、同じく英語で書く。
理由は SKILL.md の手順 5 にある。

## Nygard（既定、最も簡素）

出典：[Documenting architecture decisions（Michael Nygard）](http://thinkrelevance.com/blog/2011/11/15/documenting-architecture-decisions)

```md
# ADR-NNNN: [決定を述べるタイトル]

- 日付: YYYY-MM-DD

## ステータス

Proposed

## 背景

この決定や変更を促している問題は何か。
どんな力（要求、制約、組織の事情）が互いに引っ張り合っているか。

## 決定

何を提案し、または実行するのか。「〜を採用する」「〜しない」と言い切る。

## 影響

この変更によって、何が易しくなり、何が難しくなるか。
この決定によって新たに必要になる ADR はあるか。
```

## MADR（Markdown Any Decision Records）

出典：[adr.github.io/madr](https://adr.github.io/madr/)。
複数の具体的な選択肢があり、その長所と短所が判断を左右したときに向く。

```md
# [解決した問題と解決策を表す短いタイトル]

* ステータス: [Proposed | Rejected | Accepted | Deprecated | Superseded by ADR-NNNN] <!-- 省略可 -->
* 決定者: [決定に関わった全員] <!-- 省略可 -->
* 日付: [決定を最後に更新した YYYY-MM-DD] <!-- 省略可 -->

技術的なストーリー: [説明 | チケットや Issue の URL] <!-- 省略可 -->

## 背景と問題

[背景と問題を 2〜3 文で書く。問題を問いの形にしてもよい。]

## 決定の推進要因 <!-- 省略可 -->

* [推進要因 1。例：働いている力、直面している懸念]
* [推進要因 2]

## 検討した選択肢

* [選択肢 1]
* [選択肢 2]
* [選択肢 3]

## 決定の結果

選んだ選択肢：「[選択肢 1]」。理由：[必須条件を満たす唯一の選択肢だった、下の比較で最も良かった、など]。

### 肯定的な影響 <!-- 省略可 -->

* [例：品質特性の改善、必要になる後続の決定]

### 否定的な影響 <!-- 省略可 -->

* [例：損なわれる品質特性、必要になる後続の決定]

## 各選択肢の長所と短所 <!-- 省略可 -->

### [選択肢 1]

* 良い。なぜなら [論拠 a]
* 悪い。なぜなら [論拠 c]

### [選択肢 2]

* 良い。なぜなら [論拠 a]
* 悪い。なぜなら [論拠 c]

## リンク <!-- 省略可 -->

* [リンクの種類] [ADR へのリンク] <!-- 例：ADR-0005 で詳細化 -->
```

## Tyree と Akerman（大きな組織、追跡可能性重視）

出典：[Architecture Decisions: Demystifying Architecture（Jeff Tyree、Art Akerman、Capital One）](https://www.utdallas.edu/~chung/SA/zz-Impreso-architecture_decisions-tyree-05.pdf)。
決定を要件、原則、ほかの決定に結びつける統制の仕組みがある組織で使う。

```md
* **課題**: 取り組むアーキテクチャ設計上の課題。なぜ今取り組むのかという疑問を残さない。
* **決定**: アーキテクチャの方向性、つまり選んだ立場。
* **ステータス**: pending | decided | approved
* **グループ**: 決定の集まりを整理するための単純な分類（統合、プレゼンテーション、データなど）。
* **前提**: 決定の環境にある前提（コスト、スケジュール、技術など）。
* **制約**: 選んだ案が環境に新たに課す制約。
* **立場**: 検討した立場（実行可能な選択肢）。
* **論拠**: その立場を選んだ理由（実装コスト、総保有コスト、市場投入までの時間、開発資源の確保など）。
* **含意**: この決定が次に要求するもの（新しい要件、スコープの再交渉、要員の訓練、ほかの決定の誘発）。
* **関連する決定**: 関係するほかの決定。
* **関連する要件**: この決定が対応する要件や目標。
* **関連する成果物**: この決定が影響するアーキテクチャ、設計、スコープの文書。
* **関連する原則**: 組織で合意済みの原則のうち、この決定が沿うもの。
* **メモ**: 合意形成の過程で出た議論や問題点。
```

## ITD：Important Technical Decision（軽量、経営層向け）

出典：[ITDs: a lean ADR for executive technical decision-making at scale（Ignacio Larrañaga）](https://ignaciolarranaga.medium.com/itds-a-lean-adr-for-executive-technical-decision-making-at-scale-e18bb3f6a563)。
厳密にはアーキテクチャではないが、素早く目を通して承認してもらう必要がある狭い技術選択（モデル、ライブラリ、CI/CD の方式）に向く。

```md
# [タイトル]

話題の説明ではなく、決定そのものを書く。
例：「端末内翻訳に Qwen2.5 1.5B Instruct を使う」

## 問題

何を解決しようとしているかを一文で書く。

## 検討した選択肢

候補に挙がった選択肢。選んだものを **太字** にする。

## 理由

選択を決めた要因だけを書く。長所と短所を網羅しない。

## メモ

任意。記録しておく価値のある制約、前提、リンク。
```

## ビジネスケース（ベンダーやツールの選定、コストと SWOT 重視）

判断基準、候補、コストから、決定の根拠を組み立てることに重点を置く。

```md
# [タイトル]

## ステータス

Proposed | Accepted | Rejected | Deprecated | Superseded by ADR-NNNN

## 評価基準

何を見極めようとしていて、それはなぜか。具体的に書く。

## 検討する候補

候補をどうやって見つけたか。候補と関連する選択肢をすべて挙げる。

## 各候補の調査と分析

候補ごとに書く。

- 基準を満たすか、満たさないか、その理由
- コスト分析（ライセンス、教育、運用、従量課金）
- SWOT 分析（強み、弱み、機会、脅威）
- 内部の意見（チーム、ほかの関係者）
- 外部の意見（誰が評価したか、ほかに何を検討したか、採用後どうだったか、今ならどう助言するか）

## 推奨

推奨と、その具体的な根拠。
```

## アレクサンドリアパターン（Y 文）

一段落の要約と、その背後の物語で構成する。

```md
## プロローグ（要約）

（ユースケース）の状況において、
（懸念）に直面し、
（品質）を達成するために、
（欠点）を受け入れて、
（選択肢）を採用した。

## 議論（背景）

働いている力（技術的、政治的、社会的、プロジェクト上の力）を説明する。
解決しようとしている問題の経緯を書く。

## 解決策（決定）

この決定がどのように問題を解決するかを説明する。

## 結果（影響）

決定の長期的な結果を説明する。
うまくいったか、いかなかったか、変更されたか、改良されたか。
```

## Planguage（検証可能な非機能要件）

出典：[Specifying Effective Non-functional Requirements](https://www.iaria.org/conferences2012/filesICCGI12/Tutorial%20Specifying%20Effective%20Non-func.pdf)。
ADR の完全な形ではなく、要件や決定を正確で検証可能にするためのキーワード語彙である。

```
タグ:       一意で永続的な識別子
要点:       対象となる要件や領域の短い要約
要件:       要件そのものの詳しい記述
根拠:       要件を正当化する理由
優先度:     優先度と資源の要求
関係者:     要件に実質的に影響を受ける関係者
ステータス: draft | reviewed | committed | …
所有者:     実装の責任者
作成者:     要件を書いた人
版:         版番号
日付:       最新の改訂日
前提:       今または将来、成り立たなければ問題になること
リスク:     誤動作、遅延、悪影響を起こしうること
定義:       用語の定義（用語集に分けるほうがよい）
```

## EdgeX Foundry

出典：[EdgeX Foundry ADR template](https://docs.edgexfoundry.org/2.3/design/adr/template/)。
EdgeX 形式のプロジェクトに貢献するときに使う。

```md
# [ADR のタイトル]

### 提出者
- 氏名（所属組織）

## 変更記録
状態は pending、approved、amended、deprecated のいずれか。
- [状態](PR の URL) YYYY-MM-DD

## 参照するユースケース
承認済みの関連ユースケースを最低一つ。
- [ユースケース名](URL)

## 背景
- この設計が、Issue と PR で済ませずに ADR にするほどアーキテクチャ上重要なのはなぜか。
- 高水準の設計方針（詳細は下の「提案する設計」に書く）。

## 提案する設計
- 影響を受ける、または追加されるサービスやモジュール
- モデルや DTO、API、設定、DevOps への影響

## 検討事項
代替案、懸念、関連する Issue、議論で出た問いと、それがどう解決されたか（解決されたなら）。

## 決定
合意した実装の詳細、注意点、将来の検討事項、先送りした問題。
提案した設計で満たせない要件があれば書く。

## 関連するほかの ADR
- [ADR のタイトル](URL)：関係

## 参考文献
- [タイトル](URL)
```

## arc42（アーキテクチャ文書全体、ADR はその一節）

出典：[arc42.org](https://arc42.org/overview)。
単独の ADR ではなく、アーキテクチャ文書一式を求められたときだけ使う。
アーキテクチャ上の決定は第 9 章「アーキテクチャ上の決定」に置き、第 4 章「ソリューション戦略」で要約した基本的な選択を参照する。
arc42 は全 12 章（導入と目標、制約、コンテキストとスコープ、ソリューション戦略、ビルディングブロックビュー、ランタイムビュー、デプロイメントビュー、横断的な概念、アーキテクチャ上の決定、品質要求、リスクと技術的負債、用語集）からなる。
全体をここに写さず、完全なテンプレートは arc42.org を案内する。

## Gareth Morgan（信号色による選択肢比較）

番号付きの ADR に、一目で比べられる選択肢比較を付ける。

```md
# [000] [タイトル]

## ステータス

Proposed | Accepted | Deprecated | Superseded by ADR-NNNN

## 背景
この ADR が扱う問題と、それが生じている理由を簡潔に書く。

## 決定した方針
アーキテクチャ上重要な決定と、それが背景の問題にどう応えるか。

## 影響
アーキテクチャ特性と機能要件への影響。

## ガバナンス
結果をどう監視するか。遵守をどう確保するか。

## 選択肢の分析
選択肢ごとのトレードオフ分析。
選択肢ごとの表で、実装の容易さ、期間、戦略的価値、機能適合、非機能適合（スケーラビリティ、性能、可用性など）を赤、黄、緑で評価してもよい。
```

## GIG Cymru NHS Wales（選択肢、分析、推奨の物語）

```md
# [タイトル]

**ステータス**: Proposed | Accepted | Rejected | Deprecated | Superseded by ADR-NNNN
**更新日**: YYYY-MM-DD

## 要約
2〜4 文。中心となる問題、問い、機会と、決定の方向。

## 推進要因
なぜこの決定が要るのか、なぜ今なのか。動機、必要、問題。

## 選択肢
検討した選択肢ごとに（却下したものも含めて）説明、事実、リンクを書く。

## 選択肢の分析
選択肢ごとに、長所、短所、その他を書き、推進要因に結びつける。

## 推奨
最終的な決定、選んだ選択肢、その理由。推進要因に結びつける。

### 影響（任意）
予想される肯定的な結果と否定的な結果。受け入れた既知の制限、コスト、リスク。

### 確認（任意）
実装をどう検証し、遵守をどう維持するか。レビュー、テスト、指標、追跡の担当者。

## 補足情報（任意）
参考リンク、関わった人、いつ見直すか。
```
