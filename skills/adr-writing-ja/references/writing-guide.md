# 良い ADR を書くための点検項目とチーム運用

SKILL.md の手順 5 で、下書きを詳しく点検したいときに読む。
論証の筋の点検（手順 6）は argument-gap-edit が受け持つので、ここでは ADR の中身と運用を扱う。

## 良い ADR の性質

- **理由がある**：結果だけでなく、背景、選択肢の長所と短所、機能比較、費用対効果を書く。
- **具体的である**：一つの ADR に一つの決定を書く。まとめて書いた決定は別々のファイルに分ける。
- **日付がある**：コスト、スケジュール、規模の数値、ベンダーの条件など、時間とともに変わるものには日付を付ける。
- **既定では書き換えない**：承認済みの ADR の元の内容を書き直さない。日付付きの情報を追記するか、新しい ADR で置き換える。チームによっては「生きた文書」方式を意図して選び、決定の後に得た情報を日付と注記付きで既存の ADR に挿入する。どちらでもよいが、一つのプロジェクトの中では揃え、どちらを採っているかを明示する。

## 背景の節を書く

- 技術的な問題だけでなく、組織の実際の状況と事業上の優先順位を書く。
- 決定に効いたなら、チームの技能構成や人数も書く。
- 長所と短所は、一般論ではなく、このチームの実際の必要と目標に照らして書く。

## 影響の節を書く

- 易しくなること **と** 難しくなることを書く。
- この決定によって必要になった後続の ADR を挙げる。大きな決定が一つあると、それに続く小さな決定がいくつも必要になることが多い。
- チームが事後レビュー（たとえば一か月後に ADR と実際の結果を比べる）を行うなら、その予定をここに書く。

## ADR にすべきかを判断する

ADR を書く理由になるもの：

- 将来の開発者が、今していることの「なぜ」を理解する必要がある。
- 決定がアーキテクチャ上重要である、チームをまたぐ、または覆しにくい。

ADR を書かない理由になるもの：

- アーキテクチャに関わらない、または小さい（危険が小さく、影響が閉じていて、一人で決められる）。
- 既存の標準、方針、文書ですでに決まっている。
- 一時的である（回避策、概念実証、実験）。

## ライフサイクル（チームが正式な段階を望む場合）

よくある形は **着手 → 調査 → 評価 → 実装 → 保守 → 廃止** である。

段階を進める前に、次の問いで受け入れ条件を確かめるとよい。

- 問題ははっきり言語化されているか。
- 代替案は実際に検討されたか。
- トレードオフは理解され、記録されているか。
- 関連する背景はそろい、関係者全員が関わったか。
- 出たフィードバックはすべて反映されたか。

## ADR に名前を載せる役割（責任の所在を明確にしたい場合）

提案者、調査者、評価者、レビュアー、承認者、保守者を置く。
簡単な形としては、ADR ごとに主担当、副担当、責任を負うチームを決める。
その三者が、周知、公開、保守、定期的な見直し（たとえば少なくとも年一回）、最終的な廃止を受け持つ。

## 適応度関数：決定を記録するだけでなく検証できるようにする

決定記録は決定を記す。
**適応度関数**（fitness function）は、決定がいまも守られているかを CI で自動的かつ客観的に確かめる検査である。

- 決定の例：「監査要件のためにイベントソーシングを使う」
- 適応度関数の例：すべての状態変更がイベントを発行することを CI で確かめる。

道具：[ArchUnit](https://www.archunit.org/)（Java）、[ArchUnitTS](https://github.com/LukasNiessen/ArchUnitTS)（TypeScript、JavaScript）。

記録済みの決定に作業が沿っているかを AI に確かめさせるプロンプトを求められたら、次の形がよく機能する。

```txt
重要：事前学習の知識より、検索して得た情報に基づいて推論すること。
重要：拡張思考、専門家の助言、検索を有効にすること。

これは、私たちの作業が決定をすべて守っていて、正しく正確であるかを評価する適応度関数である。

- 私たちの決定：{url}
- 評価する作業：{url}

誤り、問題、欠落、弱点をすべて説明せよ。率直に、断定的に書くこと。
```
