# ADR 作成（日本語）

**アーキテクチャ決定記録**（Architecture Decision Record、ADR）は、重要な設計判断を一つ、その判断に至った背景と、判断がもたらす影響とともに残す短い文書である。
ADR の読み手は、その場にいなかった将来の開発者である。
その読み手が「なぜこうなっているのか」を当時の状況から再構成できることが、ADR の目的になる。

このスキルは、任意のリポジトリで日本語の ADR を一本書く手順を定める。
`references/templates.md`（テンプレート集）と `references/writing-guide.md`（執筆ガイド）は、それだけで使えるように書いてある。

## 併用するスキル

ADR の価値は、背景から決定へ、決定から影響へと筋が通っていることにある。
筋の通らない ADR は、読み手に「なぜ」を渡せない。
そのため、下書きを書き終えたら手順 6 で `../argument-gap-edit/SKILL.md` を読み、その点検手順を ADR に適用する。
argument-gap-edit は `../japanese-tech-writing/SKILL.md` を併読するよう指示しているので、文章の整形もそれに従う。

argument-gap-edit がインストールされていない場合は、手順 6 の対応表だけで点検する。

## 1. ADR にすべき決定か判断する

すべての決定に ADR が要るわけではない。
次のどれかに当たるなら ADR を勧める。

- アーキテクチャ上重要である（構造、外部インターフェース、品質特性に影響する、または覆すのに費用や危険が伴う）。
- 議論に居合わせなかった将来の開発者が、理由を知る必要がある。
- 記録する価値のあるトレードオフがあった（リンタやスタイルガイドで決まる一行の好みではない）。

次の場合は ADR を書かない。

- 小さく、影響が閉じていて、一人で決められる。
- 既存の方針や標準文書ですでに決まっている。
- 一時的な回避策、概念実証、実験である。

ユーザーが迷っているときは、決定の中身と「後で誰が理由を知る必要があるか」を尋ねる。
たいていそれで決まる。

## 2. 置き場所を決める

まず既存の慣習を探す。

```sh
git ls-files | grep -iE '(^|/)(adr|adrs|decisions?)(/|$)'
```

- 見つかれば、その置き場所、書式、番号付け、見出しの言語にそのまま合わせる。既存の ADR が英語見出しなら、新しい ADR も英語見出しにして本文だけ日本語で書く。一つのディレクトリに二つの書式が混ざると、読み手が毎回書式を読み替えることになるからだ。
- 見つからなければ、`doc/ADR/NNNN-<kebab-case>.md` を既定にする。このライブラリの external-api-tos-check と ddd-bdd-tdd-flow もこの場所を前提にしているため、同じ場所にしておけば各スキルが同じ連鎖を読める。
- ユーザーが「アーキテクチャ」という語に抵抗を示すなら、`decisions/` を提案してよい。「決定」という語のほうが、ベンダー選定やスケジュールなどアーキテクチャ以外の決定も記録しやすいからだ。

## 3. ファイル名とタイトルを決める

ファイル名は ASCII にする。

- 小文字の kebab-case で、動詞から始まる現在形の句にする（`choose-database.md`、`handle-exceptions.md`）。
- 番号付けを採るなら、4 桁ゼロ埋めの連番を前に付ける（`0007-choose-database.md`）。次の番号は、既存ファイルの最大値に 1 を足して決める。
- 日本語のファイル名は避ける。シェル、URL、一部の CI ツールで扱いにくくなるからだ。

タイトル（本文の `#` 見出し）は日本語で書き、決定そのものを述べる。
話題ではなく結論を書く。

- 悪い例：「データベースについて」
- 良い例：「業務データの永続化に PostgreSQL を採用する」

番号付けを採る場合は `# ADR-0007: 業務データの永続化に PostgreSQL を採用する` の形にする。

## 4. テンプレートを選ぶ

ユーザーの好みを聞くか、決定の形から選ぶ。
各テンプレートの骨組みは `references/templates.md` にある。

| 状況 | テンプレート |
|---|---|
| 既定、迷ったとき | **Nygard**（タイトル、ステータス、背景、決定、影響） |
| 複数の選択肢の長所と短所を軽く並べたい | **MADR** |
| 要件や原則への追跡可能性が求められる大きな組織 | **Tyree と Akerman** |
| ライブラリやモデルなど狭い技術選択に、経営層の素早い承認が要る | **ITD**（Important Technical Decision） |
| コスト、SWOT、関係者の意見を含むベンダーやツールの選定 | **ビジネスケース** |
| 一段落の要約（Y 文）と物語を組み合わせたい | **アレクサンドリアパターン** |
| 非機能要件を検証可能な形式で書きたい | **Planguage** |
| EdgeX Foundry の慣習に合わせる | **EdgeX** |
| アーキテクチャ文書全体の一節として ADR を書く | **arc42**（第 9 章） |
| 選択肢を信号色の表で比べたい | **Gareth Morgan** |
| 選択肢、分析、推奨の順で物語として書きたい | **GIG Cymru NHS Wales** |

迷ったら Nygard にする。
最も広く知られていて、道具なしでチームが使い始められるからだ。

## 5. 下書きを書く

詳しい点検項目は `references/writing-guide.md` にある。
最低限、次を守る。

- **一つの ADR に一つの決定を書く。** 互いに独立して覆りうる決定は、別のファイルに分ける。
- **背景には、せめぎ合う力を書く。** 「データベースが必要だった」ではなく、組織の状況、制約、互いに引っ張り合う要求を書く。チームの技能構成が決定に効いたなら、それも書く。
- **決定は言い切る。** 「〜を採用する」「〜しない」と書く。「検討する」「原則として」「必要に応じて」でぼかさない。
- **影響には、易しくなることと難しくなることの両方を書く。** この決定によって新たに必要になった後続の ADR もここに挙げる。
- **日付を入れる。** コスト、価格、規模の数値は古くなる。変わりうる値には、いつの値かを添える。
- **ステータスを付ける。** 値は `Proposed | Accepted | Rejected | Deprecated | Superseded by ADR-NNNN` のいずれかにする。見出しや本文は日本語でも、ステータス値は英語のまま固定する。grep や ADR ガードのような道具、このライブラリの他のスキルが、この語で連鎖をたどるからだ。
- **新しい ADR は `Proposed` で書く。** `Accepted` を付けるのは、ユーザーが「この ADR を承認する」と明示したときだけにする。「切り替えたい」「〜にすることにした」のような意図や背景の説明は、承認の指示ではない。`Accepted` は、チームがこの本文で合意したという記録だ。まだ誰も読んでいない下書きに付ければ、その記録が偽りになる。承認するかどうかは、下書きを渡すときに尋ねる。既存の ADR のステータスを `Accepted` や `Superseded by` に変えるときも、同じように明示的な確認を取る。

下書きは、ユーザーから聞いた事実だけで書く。
背景にある制約や数値をユーザーから得ていない場合は、もっともらしい値で埋めずに `<!-- 要確認：月間リクエスト数 -->` のように印を残し、何が足りないかをユーザーに伝える。
推測で埋めた背景は、決定を支えているように見えて、実は何も支えていないからだ。

## 6. argument-gap-edit で論証を点検する

下書きができたら `../argument-gap-edit/SKILL.md` を読み、その点検手順に従う。
ADR では、段落に加えて節（背景、決定、影響、またはテンプレートの対応する節）も点検の単位にする。
各節と各段落について「前から何を受けるか」「ADR の中で果たす役割」「次へ何を渡すか」を一文ずつ書き出し、書けないものをギャップ候補にする。

ADR では、argument-gap-edit の検出項目が次の形で現れやすい。

| 検出項目 | ADR での現れ方 |
|---|---|
| 証拠の型違い | 背景で挙げた力が、選んだ選択肢を支えていない。例：背景では「運用人員が 2 名しかいない」と書いたのに、決め手として性能だけを挙げている。 |
| 言い換えによる逃げ | 背景で「整合性」と書いた要求を、影響で「安定性」に替えて達成したことにする。決定の節で言い切りを避ける。 |
| 理論の見せびらかし | CAP 定理や一般的な長所短所の羅列が、選択を一つも変えていない。 |
| 話題の飛び込み | 決定の根拠に、背景で一度も出ていない要求が突然現れる。 |
| 術語の先出し | 「結果整合性」「ヘキサゴナル」などの術語を、具体的な関係を述べる前に立てて理解したことにする。 |
| A-B-A の割り込み | 選択肢の比較の途中に別の決定の話が挟まる。これは一つの ADR に二つの決定が入っている兆候なので、挟まった話を別の ADR に分ける。 |
| コラムの空転 | 「補足」「参考」の節が、読み手の次の判断を何も変えていない。 |

加えて、ADR 特有の筋として次を確かめる。

- 影響に書いた「難しくなること」が、背景で挙げた力のうちどれを犠牲にした結果なのか対応づけられる。対応づけられない「難しくなること」は、背景に書き漏らした力があることを示している。
- 却下した選択肢それぞれについて、却下の理由が背景の力のどれかに結びついている。

修正は argument-gap-edit の修正方針に従う。
ただし点検の対象は、まだ `Proposed` の下書きに限る。
`Accepted` になった ADR の本文は、手順 7 に従って書き換えない。

## 7. 書き換えずに置き換える

承認済みの ADR は、原則として書き換えない。
当時の判断を当時の文脈のまま残すことが、ADR の記録としての価値だからだ。
チームによっては、日付付きの追記で更新する「生きた文書」方式を採ることもある。
どちらの方式かわからなければユーザーに尋ね、一つのプロジェクトの中ではどちらかに揃える。

新しい決定が古い決定を置き換えるときは、次の二段階で進める。

1. **下書きの段階。** 新しい決定を `Proposed` の新しい ADR として書く。そのステータス欄またはリンク欄に `Supersedes [ADR-MMMM](MMMM-<slug>.md)` と書き、古い ADR へ戻れるようにする。古い ADR にはまだ触れない。新しい ADR が承認されるまでは、古い決定が有効なままだからだ。
2. **承認の段階。** ユーザーが新しい ADR の承認を明示したら（手順 5）、同じ変更で二つを行う。新しい ADR のステータスを `Accepted` にする。古い ADR のステータスを `Superseded by [ADR-NNNN](NNNN-<slug>.md)` に変える。古い ADR の本文には触れない。

下書きを渡すときは、承認するかどうかと、承認すれば古い ADR のステータスも変わることをユーザーに伝える。

## 8. 任意：プルリクエストへの組み込み

ADR の有無を PR で強制したい、または関連する ADR を PR に表示したいとユーザーが望んだときだけ、次を紹介する。
頼まれていないのに設定はしない。

- [ADR Guard](https://github.com/chohan-sarmad-ali/delivery-gates)：監視対象のコードが変わったのに ADR が追加も更新もされていない PR を失敗させる GitHub Action。`ADR-Exempt:` による免除を扱える。
- [Decision Guardian](https://github.com/DecispherHQ/decision-guardian)：PR が触れたコードに関係する既存の決定記録を PR 上に表示する。

背景知識やほかのテンプレートは、上流の [architecture-decision-record リポジトリ](https://github.com/joelparkerhenderson/architecture-decision-record) にある。
日本語訳は同リポジトリの `locales/ja/` にある。

## 仕上げの確認

ADR を渡す前に、次を確かめる。

- タイトルが話題ではなく決定を述べている。
- ステータスと日付がある。
- 手順 6 の点検で、書き出せない「受ける」「役割」「渡す」が残っていない。
- `<!-- 要確認 -->` の印が残っているなら、何を確認すべきかをユーザーへの返答にまとめた。
- ユーザーが承認を明示していない ADR は `Proposed` のままにし、承認するかを返答で尋ねた。
- 置き換えの場合、承認前なら古い ADR に触れていない。承認後なら、古い ADR の `Superseded by` を同じ変更に含めた。
